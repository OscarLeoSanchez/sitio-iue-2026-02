Plaza: formularios, validación y base de datos

Autor/a

Oscar Leonel Sánchez Conde

Fecha de publicación

31 de octubre de 2026

Qué construyes Plaza, un servidor ASP.NET Core MVC con catálogo, detalle de producto y pedidos, con formularios que se validan en el navegador y en el servidor, y catálogo y pedidos guardados en una base de datos PostgreSQL con Entity Framework Core, consultados con LINQ
Prerrequisitos Una terminal, Git instalado y nociones de C# (clases, listas y métodos). Parte de cero: no necesitas otra guía
Herramientas .NET SDK 10 (10.0.302), VS Code, Git, PowerShell y PostgreSQL 18.6 en versión portable

Presentación interactiva: el recorrido de un pedido desde el formulario hasta la base de datos, con diagramas y el código de cada paso

Abrir la presentación

NotaCómo usar esta guía

  • Los comandos de dotnet se ejecutan dentro de la carpeta Plaza, la que crea la primera etapa.
  • Cada archivo aparece completo con su ruta encima. Si un archivo cambia en una etapa posterior, la guía lo muestra completo otra vez: reemplaza todo su contenido.
  • Cada etapa termina con una sección Comprueba. No sigas a la etapa siguiente hasta que se cumpla.
  • Al cerrar una etapa que funciona, guarda un commit. Si algo se rompe después, vuelves a ese punto.

Etapa 1. Crear el proyecto vacío

Qué vas a lograr

Un servidor mínimo que responde Hello World! en tu equipo.

Los comandos

Ubícate en la carpeta donde guardes tus proyectos y ejecuta:

dotnet new web -n Plaza
cd Plaza
dotnet run
  • dotnet new web crea un proyecto web de ASP.NET Core mínimo. No trae controladores, vistas ni base de datos: los agregas tú, etapa por etapa.
  • -n Plaza fija el nombre del proyecto y de su carpeta. Escribe Plaza con mayúscula: en C# esa es la convención para nombres de proyecto y de clase.
  • dotnet run compila y arranca el servidor. Se detiene con Ctrl + C.

Los archivos que se generan

Archivo Para qué sirve
Plaza.csproj La ficha del proyecto: versión de .NET y paquetes
Program.cs El punto de entrada: arma y arranca el servidor
appsettings.json Configuración de la aplicación
Properties/launchSettings.json El puerto y el entorno cuando ejecutas en tu equipo

Comprueba

dotnet run imprime una dirección como http://localhost:5079. Ábrela en el navegador: debe mostrar Hello World!. El puerto puede ser otro en tu equipo; usa el que imprima tu terminal.

Etapa 2. Entender Program.cs

Abre Program.cs. Son seis líneas y ahí está la base de todo lo que construyes:

Program.cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => "Hello World!");

app.Run();
  1. builder es la fase de preparación. Aquí registras los servicios que necesita la aplicación: controladores, base de datos, inyección de dependencias.
  2. Build() cierra esa preparación y crea la aplicación. Después de esta línea ya no puedes registrar servicios.
  3. MapGet es una ruta: cuando llega un GET a /, responde ese texto.
  4. Run() deja el servidor escuchando peticiones hasta que lo detengas.

Guarda este patrón: registrar servicios, construir, configurar rutas, ejecutar. El proyecto final tiene el mismo orden, solo que más grande.

Etapa 4. Las carpetas y el modelo Producto

Qué vas a lograr

Una estructura de carpetas donde cada cosa tiene su lugar, y la primera clase del negocio.

Las carpetas

mkdir Models, Services, Controllers, Views

Cada carpeta responde una pregunta:

Carpeta Pregunta que responde
Models ¿Qué datos manejo?
Services ¿Dónde vive la lógica?
Controllers ¿Quién atiende las peticiones?
Views ¿Qué ve el usuario?

Git no guarda carpetas vacías: aparecen en el repositorio cuando tengan su primer archivo.

El modelo

Models/Producto.cs
public class Producto
{
    public int Id { get; set; }
    public string Nombre { get; set; } = string.Empty;
    public decimal Precio { get; set; }
}
  • Un modelo es una clase que describe un dato del negocio. Esta carpeta guarda datos, no lógica.
  • Id identifica cada producto. Cuando lleguen a la base de datos será la clave primaria.
  • = string.Empty evita que Nombre quede nulo: el proyecto tiene Nullable activado y sin esto el compilador avisa.
  • decimal es el tipo para dinero. double tiene errores de redondeo (0.1 más 0.2 no da exactamente 0.3).
NotaSobre los namespace

Esta guía deja las clases en el espacio global para mantener el código corto. En un proyecto grande cada carpeta tiene su propio namespace (por ejemplo Plaza.Models) y los archivos que usan esas clases agregan el using correspondiente. Funciona igual en este tamaño.

Comprueba

dotnet build termina con 0 Errores.

Etapa 5. El contrato del catálogo y su servicio

Qué vas a lograr

Un catálogo de productos que el resto del programa usa sin saber de dónde salen los datos.

El contrato

Services/ICatalogo.cs
public interface ICatalogo
{
    List<Producto> Listar();

    Producto? Buscar(int id);
}

Una interfaz es un contrato: dice qué sabe hacer un catálogo (listar y buscar) sin decir cómo. Va primero a propósito: más adelante cambias la lista en memoria por una base de datos y quien usa el catálogo no se entera. Producto? lleva el signo de pregunta porque Buscar puede no encontrar nada.

La primera implementación

Services/CatalogoEnMemoria.cs
public class CatalogoEnMemoria : ICatalogo
{
    private readonly List<Producto> productos = new()
    {
        new Producto { Id = 1, Nombre = "Tomate", Precio = 3500m },
        new Producto { Id = 2, Nombre = "Aguacate", Precio = 6000m },
        new Producto { Id = 3, Nombre = "Papa", Precio = 2800m },
        new Producto { Id = 4, Nombre = "Panela", Precio = 4500m },
    };

    public Producto? Buscar(int id)
    {
        return productos.FirstOrDefault(p => p.Id == id);
    }

    public List<Producto> Listar()
    {
        return productos;
    }
}

La clase cumple el contrato guardando la lista dentro del programa. La m en 3500m marca el número como decimal; sin ella C# lo toma como double.

Comprueba

dotnet build termina sin errores. Todavía no se ve nada nuevo en el navegador.

Etapa 6. Registrar el servicio y mostrar el catálogo

Qué vas a lograr

Que /catalogo muestre los productos.

Registrar servicios en Program.cs

Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllersWithViews();
builder.Services.AddSingleton<ICatalogo, CatalogoEnMemoria>();

var app = builder.Build();

app.MapControllers();

app.Run();
  • AddControllersWithViews activa los controladores y las vistas Razor.
  • AddSingleton<ICatalogo, CatalogoEnMemoria> le dice a ASP.NET Core: cuando alguien pida un ICatalogo, entrégale un CatalogoEnMemoria, siempre el mismo objeto (singleton), para que la lista no se reinicie en cada petición.
  • MapControllers conecta las rutas que declaran los controladores con el servidor.
  • El MapGet de Hello World! ya no hace falta.

El controlador

Controllers/CatalogoController.cs
using Microsoft.AspNetCore.Mvc;

public class CatalogoController : Controller
{
    private readonly ICatalogo catalogo;

    public CatalogoController(ICatalogo catalogo)
    {
        this.catalogo = catalogo;
    }

    [HttpGet("catalogo")]
    public IActionResult Listar()
    {
        return View(catalogo.Listar());
    }
}

Un controlador recibe la petición, pide lo que necesita y decide la respuesta.

  • El constructor pide un ICatalogo. Esto es la inyección de dependencias: el controlador no crea el catálogo, lo recibe.
  • [HttpGet("catalogo")] es la ruta: un GET a /catalogo ejecuta Listar. El nombre del método no cambia la dirección; la define el atributo.
  • View(...) entrega la lista a la vista.

La vista

Views/Catalogo/Listar.cshtml
@model List<Producto>
<!DOCTYPE html>
<html lang="es">

<head>
    <meta charset="utf-8">
    <title>Catálogo - Plaza Campesina</title>
</head>

<body>
    <h1>Catálogo</h1>

    <ul>
        @foreach (var producto in Model)
        {
            <li>@producto.Nombre - $@producto.Precio</li>
        }
    </ul>
</body>

</html>
  • @model declara qué dato recibe la vista, y Model es ese dato.
  • ASP.NET Core busca la vista en Views/<Controlador>/<Método>.cshtml. Por eso este archivo va en Views/Catalogo/ y se llama Listar.cshtml, igual que el método. Si el nombre del método y el del archivo no coinciden, la página responde 500 con el mensaje The view 'Listar' was not found.
TipUna regla para todo el proyecto

El nombre del método del controlador y el de su vista siempre coinciden.

Comprueba

Ejecuta dotnet run y abre /catalogo: aparecen los cuatro productos. Guarda el commit:

git add .
git commit -m "feat: catalogo en memoria"

Etapa 7. El detalle de un producto

Qué vas a lograr

Una página por producto, con una ruta que recibe el Id en la dirección.

El controlador con el método nuevo

Controllers/CatalogoController.cs
using Microsoft.AspNetCore.Mvc;

public class CatalogoController : Controller
{
    private readonly ICatalogo catalogo;

    public CatalogoController(ICatalogo catalogo)
    {
        this.catalogo = catalogo;
    }

    [HttpGet("catalogo")]
    public IActionResult Listar()
    {
        return View(catalogo.Listar());
    }

    [HttpGet("catalogo/{id:int:min(1)}")]
    public IActionResult Buscar(int id)
    {
        var producto = catalogo.Buscar(id);
        if (producto is null)
        {
            return NotFound();
        }
        return View(producto);
    }
}
  • {id} es un parámetro de la ruta: lo que venga en esa parte de la dirección llega al método como id.
  • int:min(1) es una restricción: solo atiende enteros desde 1. /catalogo/abc y /catalogo/0 ni llegan al método.
  • Si el producto no existe, NotFound() responde 404 en lugar de fallar con un error.

Los tag helpers

Views/_ViewImports.cshtml
@addTagHelper *, Microsoft.AspNetCore.Mvc.TagHelpers

Un tag helper es un atributo especial (asp-action, asp-route-id) que ASP.NET Core convierte en HTML normal. Esta línea los activa para todas las vistas. Sin ella, el navegador recibiría esos atributos sin procesar y los enlaces quedarían sin href.

La vista del detalle

Views/Catalogo/Buscar.cshtml
@model Producto
<!DOCTYPE html>
<html lang="es">

<head>
    <meta charset="utf-8">
    <title>@Model.Nombre - Plaza Campesina</title>
</head>

<body>
    <h1>@Model.Nombre</h1>
    <p>Precio: $@Model.Precio</p>

    <p><a asp-action="Listar">Volver al catálogo</a></p>
</body>

</html>

El archivo se llama Buscar.cshtml porque el método se llama Buscar.

Enlaces desde el listado

Cambia la vista del listado para que cada producto sea un enlace:

Views/Catalogo/Listar.cshtml
@model List<Producto>
<!DOCTYPE html>
<html lang="es">

<head>
    <meta charset="utf-8">
    <title>Catálogo - Plaza Campesina</title>
</head>

<body>
    <h1>Catálogo</h1>

    <ul>
        @foreach (var producto in Model)
        {
            <li><a asp-action="Buscar" asp-route-id="@producto.Id">@producto.Nombre</a> - $@producto.Precio</li>
        }
    </ul>
</body>

</html>
  • asp-action="Buscar" apunta al método Buscar del controlador.
  • asp-route-id="@producto.Id" rellena el {id} de la ruta con el Id de ese producto. Para el Aguacate el enlace resulta /catalogo/2.
  • No escribes la dirección a mano: ASP.NET Core la arma desde la ruta. Si mañana cambia la ruta, los enlaces siguen funcionando.

Comprueba

Detén el servidor con Ctrl + C y vuelve a ejecutar dotnet run: las vistas se compilan al arrancar, así que un cambio en una vista no se ve sin reiniciar.

Dirección Respuesta esperada
/catalogo La lista, con cada nombre como enlace
/catalogo/2 El detalle del Aguacate, 200
/catalogo/99 404: el producto no existe
/catalogo/0 y /catalogo/abc 404: la restricción los rechaza

git commit -m "feat: detalle de producto con ruta y parametro"

Etapa 8. Los pedidos: modelos y servicio

Qué vas a lograr

Las clases y el servicio que reciben y guardan pedidos. Todavía no se ve nada en el navegador.

Los dos modelos

Models/NuevoPedido.cs
using System.ComponentModel.DataAnnotations;

public class NuevoPedido
{
    [Required(ErrorMessage = "El nombre del cliente es obligatorio")]
    [StringLength(60, MinimumLength = 3, ErrorMessage = "El nombre debe tener entre 3 y 60 letras")]
    public string Cliente { get; set; } = string.Empty;

    public string Producto { get; set; } = string.Empty;

    [Required(ErrorMessage = "La cantidad es obligatoria")]
    [Range(1, 100, ErrorMessage = "La cantidad debe estar entre 1 y 100")]
    public int Cantidad { get; set; } = 1;
}
Models/Pedido.cs
public class Pedido
{
    public int Id { get; set; }
    public string Cliente { get; set; } = string.Empty;
    public string Producto { get; set; } = string.Empty;
    public int Cantidad { get; set; }
}

Son dos clases porque son dos cosas distintas:

  • NuevoPedido es lo que el cliente envía. Todavía no tiene Id y no es de fiar: puede traer cualquier cosa.
  • Pedido es lo que el servidor ya aceptó y guardó, con su número.

Los atributos entre corchetes ([Required], [StringLength], [Range]) son anotaciones de datos. Escriben la regla junto al dato que protegen, y ASP.NET Core las revisa solo cuando llega el formulario.

Las tres clases del modelo deben ser public. Si declaras class NuevoPedido sin public, el compilador responde CS0051: Inconsistent accessibility: una clase sin modificador es visible solo dentro del proyecto, y un método público no puede exigir un parámetro menos visible que él mismo.

El servicio de pedidos

Services/IPedidos.cs
public interface IPedidos
{
    Pedido Guardar(NuevoPedido nuevo);

    Pedido? Buscar(int id);
}
Services/PedidosEnMemoria.cs
public class PedidosEnMemoria : IPedidos
{
    private readonly List<Pedido> pedidos = new();

    public Pedido Guardar(NuevoPedido nuevo)
    {
        var pedido = new Pedido
        {
            Id = pedidos.Count + 1,
            Cliente = nuevo.Cliente,
            Producto = nuevo.Producto,
            Cantidad = nuevo.Cantidad,
        };
        pedidos.Add(pedido);
        return pedido;
    }

    public Pedido? Buscar(int id)
    {
        return pedidos.FirstOrDefault(p => p.Id == id);
    }
}

Es el mismo patrón del catálogo: un contrato y una implementación en memoria. Guardar convierte un NuevoPedido en un Pedido con su número.

Registrar el servicio

Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllersWithViews();
builder.Services.AddSingleton<ICatalogo, CatalogoEnMemoria>();
builder.Services.AddSingleton<IPedidos, PedidosEnMemoria>();

var app = builder.Build();

app.MapControllers();

app.Run();

Etapa 9. El formulario de pedido

Qué vas a lograr

Un formulario que envía un pedido, lo valida en el servidor y muestra una página de confirmación.

El controlador completo

El controlador recibe ahora también IPedidos y suma tres métodos.

Controllers/CatalogoController.cs
using Microsoft.AspNetCore.Mvc;

public class CatalogoController : Controller
{
    private readonly ICatalogo catalogo;
    private readonly IPedidos pedidos;

    public CatalogoController(ICatalogo catalogo, IPedidos pedidos)
    {
        this.catalogo = catalogo;
        this.pedidos = pedidos;
    }

    [HttpGet("catalogo")]
    public IActionResult Listar()
    {
        return View(catalogo.Listar());
    }

    [HttpGet("catalogo/{id:int:min(1)}")]
    public IActionResult Buscar(int id)
    {
        var producto = catalogo.Buscar(id);
        if (producto is null)
        {
            return NotFound();
        }
        return View(producto);
    }

    [HttpGet("catalogo/{id:int:min(1)}/pedir")]
    public IActionResult Pedir(int id)
    {
        var producto = catalogo.Buscar(id);
        if (producto is null)
        {
            return NotFound();
        }
        return View(new NuevoPedido { Producto = producto.Nombre });
    }

    [HttpPost("catalogo/pedir")]
    [ValidateAntiForgeryToken]
    public IActionResult Confirmar(NuevoPedido nuevo)
    {
        if (!ModelState.IsValid)
        {
            return View("Pedir", nuevo);
        }

        var pedido = pedidos.Guardar(nuevo);
        return RedirectToAction(nameof(Gracias), new { id = pedido.Id });
    }

    [HttpGet("catalogo/gracias/{id:int:min(1)}")]
    public IActionResult Gracias(int id)
    {
        var pedido = pedidos.Buscar(id);
        if (pedido is null)
        {
            return NotFound();
        }
        return View(pedido);
    }
}
  • Pedir (GET) muestra el formulario con el producto ya elegido.
  • Confirmar (POST) recibe lo enviado. ASP.NET Core llena un NuevoPedido con los campos del formulario y revisa sus anotaciones. ModelState.IsValid dice si todo cumple.
  • Si no es válido, devuelve el mismo formulario con los errores. Aquí escribes View("Pedir", nuevo) con el nombre porque es el único caso donde el método (Confirmar) y la vista (Pedir) no coinciden.
  • Si es válido, guarda y redirige a Gracias. Redirigir después de un POST evita que, al recargar la página, el navegador reenvíe el formulario y duplique el pedido.
  • [ValidateAntiForgeryToken] rechaza con 400 cualquier envío que no traiga el token que el formulario genera solo. Evita que otro sitio envíe pedidos a nombre del usuario.

Qué vas a lograr

Que los productos salgan de una base de datos real y no de una lista dentro del programa. Usas Entity Framework Core (EF Core), un ORM: una librería que traduce entre las tablas de la base y las clases de C#, sin que escribas el SQL a mano.

Instalar PostgreSQL sin administrador

El motor es PostgreSQL porque se instala sin permisos de administrador: es un .zip que se descomprime.

  1. Descarga los binarios de la versión 18.6 (unos 344 MB): https://get.enterprisedb.com/postgresql/postgresql-18.6-1-windows-x64-binaries.zip
  2. Descomprime el archivo en una carpeta postgres dentro de tu carpeta de usuario, de modo que quede postgres\pgsql\bin. En PowerShell, esa carpeta es $env:USERPROFILE\postgres.
  3. Agrega la carpeta bin a tu variable Path de usuario (no pide permisos de administrador):
$bin = "$env:USERPROFILE\postgres\pgsql\bin"
[Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path", "User") + ";" + $bin, "User")
  1. Cierra y abre de nuevo la terminal: la variable solo se carga en terminales nuevas. Comprueba:
postgres --version

Debe responder postgres (PostgreSQL) 18.6.

Los comandos de esta guía no llevan tu nombre de usuario escrito: $env:USERPROFILE es una variable de Windows que vale la carpeta de usuario de quien ejecuta el comando (C:\Users\maria en un equipo, C:\Users\carlos en otro). Si descomprimiste PostgreSQL en otro lugar, cambia solo esa parte de la ruta.

NotaProgramas y datos son carpetas distintas

Agregar bin al Path solo te permite escribir pg_ctl o psql sin la ruta completa del programa. No dice dónde están los datos: eso lo indican las opciones -D (la carpeta de datos, que initdb crea) y -l (el archivo de registro).

Crear el servidor y arrancarlo

La primera vez, initdb crea la carpeta de datos. Después solo arrancas el servidor:

initdb -D "$env:USERPROFILE\postgres\data" -U postgres -A trust --encoding=UTF8
pg_ctl -D "$env:USERPROFILE\postgres\data" -l "$env:USERPROFILE\postgres\pg.log" start
psql -U postgres -c "select version();"
  • initdb prepara la carpeta de datos con el usuario postgres. Se hace una sola vez.
  • -A trust deja entrar sin contraseña desde el mismo equipo. Sirve para la clase y nunca para un servidor real.
  • pg_ctl start arranca el servidor en el puerto 5432 y guarda su registro en pg.log. No encadenes su salida con | hacia otro comando: la terminal se queda esperando.
  • psql debe mostrar PostgreSQL 18.6. Si lo escribes sin -U postgres, falla con no existe el rol y tu nombre de usuario de Windows, porque intenta entrar con ese usuario.

Para detenerlo y para saber si está arriba:

pg_ctl -D "$env:USERPROFILE\postgres\data" stop
pg_isready -h localhost -p 5432

pg_isready responde aceptando conexiones cuando el servidor está arriba.

using Microsoft.EntityFrameworkCore;

public class PlazaDbContext : DbContext
{
    public PlazaDbContext(DbContextOptions<PlazaDbContext> options) : base(options)
    {
    }

    public DbSet<Producto> Productos => Set<Producto>();

    protected override void OnModelCreating(ModelBuilder modelo)
    {
        modelo.Entity<Producto>().Property(p => p.Nombre).HasMaxLength(60);
        modelo.Entity<Producto>().Property(p => p.Precio).HasPrecision(10, 2);

        modelo.Entity<Producto>().HasData(
            new Producto { Id = 1, Nombre = "Tomate", Precio = 3500m },
            new Producto { Id = 2, Nombre = "Aguacate", Precio = 6000m },
            new Producto { Id = 3, Nombre = "Papa", Precio = 2800m },
            new Producto { Id = 4, Nombre = "Panela", Precio = 4500m });
    }
}
  • El DbContext es la conexión con la base de datos. Cada DbSet es una tabla: Productos será la tabla de productos.

Etapa 13. Los pedidos en la base de datos

Qué vas a lograr

Que los pedidos sobrevivan al reinicio del servidor. Hoy PedidosEnMemoria guarda los pedidos en una lista dentro del programa: si detienes y arrancas dotnet run, la lista vuelve vacía. En esta etapa los pedidos pasan a una tabla de PostgreSQL, y para eso aprendes la idea central de una base de datos relacional: relacionar una tabla con otra.

La idea: dos tablas que se apuntan

Un pedido no guarda el nombre del producto como texto suelto. Guarda el número del producto, y ese número apunta a una fila de la tabla Productos:

Palabra Qué significa En Plaza
Tabla Una colección de filas con las mismas columnas Productos y Pedidos
Fila Un registro de la tabla El Aguacate, o el pedido número 1
Columna Un dato de cada fila Nombre, Precio, Cantidad
Clave primaria La columna que identifica cada fila de forma única Id en las dos tablas
Clave foránea Una columna que guarda la clave primaria de otra tabla ProductoId en Pedidos, que apunta a Id en Productos
Relación uno a muchos Una fila de una tabla se relaciona con varias de otra Un producto aparece en muchos pedidos; cada pedido tiene un solo producto

Guardar el número y no el nombre evita repetir datos: si el precio o el nombre del producto cambian, cambian en un solo lugar, la tabla Productos.

El modelo Pedido con su relación

Models/Pedido.cs
public class Pedido
{
    public int Id { get; set; }
    public string Cliente { get; set; } = string.Empty;
    public int Cantidad { get; set; }
    public int ProductoId { get; set; }
    public Producto Producto { get; set; } = null!;
}
  • ProductoId es la clave foránea: la columna que se guarda en la tabla.
  • Producto es una propiedad de navegación: no es una columna, es el objeto Producto completo al que apunta ProductoId. EF Core entiende por convención que ProductoId y Producto van juntos.
  • = null! le dice al compilador “esta propiedad no es nula, EF Core la llena cuando le pides el producto con Include”. Sin eso, el compilador avisa porque Producto no se inicializa en el constructor.
  • Cambió la forma del Pedido: ya no tiene un string Producto. Por eso la vista Gracias y los servicios cambian en esta misma etapa.

Etapa 14. Consultar con LINQ

Qué vas a lograr

Una página /pedidos que lista los pedidos guardados y que se puede filtrar por cantidad mínima. Con ella ves cómo una consulta escrita en C# se convierte en SQL.

La idea: preguntar en C#, responder en SQL

LINQ son métodos de C# (Where, OrderBy, Select) que describen una consulta sobre una colección. Cuando esa colección es una tabla (db.Pedidos), EF Core traduce la cadena de métodos a una sola consulta SQL y la ejecuta en PostgreSQL. No escribes SQL: escribes C# y EF Core lo escribe por ti.

En C# En SQL
db.Pedidos FROM "Pedidos"
.Include(p => p.Producto) INNER JOIN "Productos"
.Where(p => p.Cantidad >= minimo) WHERE p."Cantidad" >= @minimo
.OrderByDescending(p => p.Cantidad) ORDER BY p."Cantidad" DESC
.ToList() Ejecuta la consulta y devuelve la lista

La consulta no se ejecuta cuando la escribes: se ejecuta cuando la pides con ToList(), First(), Any() o un método parecido. Hasta ese momento EF Core solo va armando la descripción de lo que quieres.

    {

    }

    public Pedido Guardar(NuevoPedido nuevo)
    {

INNER JOIN "Productos" AS p0 ON p."ProductoId" = p0."Id"

ORDER BY p."Cantidad" DESC

Es la traducción de ListarGrandes, línea por línea según la tabla de arriba. Y estas son las consultas de las otras llamadas que ya usabas, para que veas cómo se traduce cada método de LINQ:

Llamada en C# SQL que ejecuta
db.Productos.OrderBy(p => p.Nombre).ToList() SELECT p."Id", p."Nombre", p."Precio" FROM "Productos" AS p ORDER BY p."Nombre"
db.Productos.Any(p => p.Nombre == nombre) SELECT EXISTS ( SELECT 1 FROM "Productos" AS p WHERE p."Nombre" = @nombre)
db.Productos.Find(id) SELECT p."Id", p."Nombre", p."Precio" FROM "Productos" AS p WHERE p."Id" = @p LIMIT 1
AdvertenciaUn error clásico: filtrar después de traer todo

Si escribes db.Pedidos.ToList().Where(p => p.Cantidad >= minimo), ToList() se ejecuta primero: trae todos los pedidos de la base a la memoria del programa y recién ahí C# filtra. El resultado es el mismo, pero con un millón de pedidos el programa los carga todos. Con el filtro antes de ToList(), el WHERE viaja a PostgreSQL y solo regresan los pedidos que cumplen. Regla: filtra, ordena y une antes de ToList().

Etapa 15. Práctica final: el teléfono del cliente

Qué vas a lograr

Aplicar todo lo anterior sin guía: agregar un dato nuevo al pedido, validarlo y guardarlo en la base de datos. Es una práctica, no tiene nota. Intenta resolverla antes de abrir la solución.

El enunciado

Cada pedido debe poder llevar el teléfono del cliente:

  • Es opcional: un pedido sin teléfono sigue siendo válido.
