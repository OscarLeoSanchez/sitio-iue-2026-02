Plaza: actividad evaluativa

Agregas un módulo nuevo al sitio y le pones una API a todo lo que Plaza ya tiene y a lo que acabas de construir. Son dos evaluaciones separadas: la Parte A es el módulo con vistas y la Parte B es la API.

Cómo se trabaja Parte A: Productores Parte B: API Orden sugerido

Cómo se trabaja y cómo se evalúa

  • Punto de partida: tu proyecto Plaza tal como quedó en la clase anterior. Los productos vienen de PostgreSQL con Entity Framework Core y los pedidos se guardan en memoria. No necesitas cambiar nada de eso.
  • Repositorio de la actividad: iue-web-plaza, el punto de partida donde quedó la sesión anterior.
  • En equipo: pueden trabajar juntos y entregar un solo proyecto por equipo.
  • La evaluación es individual: cada integrante sustenta por separado, con el código abierto, y responde por su cuenta. Lo que se pregunta es el flujo y qué hace cada pieza, no la sintaxis de memoria.
  • Dos evaluaciones separadas: la Parte A y la Parte B tienen cada una su valoración.
  • Requisito para sustentar: el proyecto compila y arranca con dotnet run.

Guías de apoyo

  • Plaza: formularios, validación y base de datos. Es la guía de la Parte A: modelo, servicio, controlador, vistas y validación.
  • Plaza: una API propia consumida desde el frontend. Es la guía de la Parte B: la API sobre los mismos servicios.

Qué no se pide en esta actividad: diseño o estilos, editar o borrar, inicio de sesión, documentación OpenAPI o Scalar, ni una página que consuma la API con fetch. Las vistas pueden ser HTML simple como las de Views/Catalogo.

A3. El contrato del servicio

public interface IProductores
{
    List<Productor> Listar();

    Productor? Buscar(int id);

    Productor Guardar(NuevoProductor nuevo);

Parte B

Una API para todo Plaza

Siete rutas que devuelven JSON: cuatro sobre lo que ya existía y tres sobre Productores. No copias lógica: usan los mismos servicios que el sitio.

Guía de apoyo: Plaza: una API propia consumida desde el frontend. Te sirven la etapa 1 (leer) y la etapa 2 (escribir). Las etapas 3 y 4 no se piden.

B1. Reglas que valen para las tres controladoras

  • Cada controlador de la API lleva [ApiController] y una ruta base que empieza por api/.
  • Los controladores reciben ICatalogo, IPedidos o IProductores por el constructor. No se crean servicios nuevos para la API.
  • La regla de los pedidos se aplica igual que en el sitio: el cliente, la cantidad y que el producto exista. No la escribes dos veces diferente.
  • Lo que crea la API se ve en el sitio y lo que crea el sitio se ve en la API, porque es el mismo servicio con los mismos datos.
  • Los controladores de MVC que ya funcionan no se modifican.

B5. Cómo probar tus rutas

Prueba cada ruta con la herramienta que prefieras: Postman, Thunder Client (la extensión de VS Code), Scalar si ya la tienes de la guía, curl.exe o cualquier otra. Los GET también funcionan en el navegador, pero no te muestran el estado ni los encabezados con claridad. El puerto es el que muestra dotnet run.

En Postman o Thunder Client, para cada ruta:

  1. Elige el verbo (GET o POST) y escribe la dirección completa, por ejemplo http://localhost:5138/api/productores/2.
  2. En los POST, abre la pestaña del cuerpo (Body), elige raw con formato JSON (en Thunder Client, la opción JSON) y pega el cuerpo de B4. La herramienta agrega el encabezado Content-Type: application/json; si la tuya no lo hace, agrégalo tú.
  3. Envía y revisa tres cosas en la respuesta: el estado (200, 201, 400 o 404), los encabezados (en un 201 busca Location) y el cuerpo (el JSON o los mensajes de error).
  4. Compara contra lo que dice B4 para esa ruta. Si no coincide, el problema está en tu código.

Si prefieres la consola, estos son los mismos casos con curl.exe en PowerShell (en Windows PowerShell 5.1, curl a secas es otro comando):

curl.exe -i http://localhost:5138/api/productores/99

'{"nombre":"Carlos Pineda","vereda":"El Roble"}' | curl.exe -i -s -X POST http://localhost:5138/api/productores -H "Content-Type: application/json" --data-binary "@-"

'{"cliente":"Ana Gomez","producto":"Mango","cantidad":2}' | curl.exe -i -s -X POST http://localhost:5138/api/pedidos -H "Content-Type: application/json" --data-binary "@-"

Recomendación: guarda las siete peticiones en una colección de tu herramienta, para repetirlas rápido cada vez que cambies algo.

B7. Lo que debes demostrar que conoces y manejas

  • Explicar qué diferencia hay entre un controlador de MVC y uno de API: qué devuelve cada uno y quién consume esa respuesta.
  • Explicar la idea de las dos puertas con un solo servicio: qué parte del trabajo se comparte entre el sitio y la API y qué parte es propia de cada puerta.
  • Explicar qué significan los estados 200, 201, 400 y 404, en qué situación devuelve tu código cada uno y por qué ese y no otro.
  • Explicar qué es el encabezado Location y por qué un POST que crea algo lo devuelve.
  • Explicar qué hace [ApiController] cuando el cuerpo recibido no cumple las anotaciones, y en qué caso tuviste que producir el 400 tú mismo (el producto que no existe).
  • Explicar cómo un cuerpo JSON se convierte en un NuevoPedido o un NuevoProductor, y cómo el objeto que devuelves se convierte en JSON, incluidos los nombres de las propiedades.
  • Probar una ruta de la API: leer el estado, los encabezados y el cuerpo de la respuesta, y distinguir un error tuyo de un error del cliente.
  • Explicar por qué lo creado por la API aparece en el sitio y al revés, y qué ocurre con esos datos cuando se reinicia la aplicación según el almacenamiento que elegiste.
