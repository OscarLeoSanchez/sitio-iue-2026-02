La red por dentro

El catálogo vive en otro computador. ¿Qué ocurre exactamente entre pedirlo y verlo en pantalla?

Modelo mental

Todo es una conversación de dos mensajes

HTTPEl idioma de esa conversación
HTTP es el protocolo con el que un cliente le pide algo a un servidor. Cada intercambio es una petición y una respuesta, ambas en texto con un formato fijo. Por eso un frontend en JavaScript entiende a un backend en C#: no comparten lenguaje, comparten formato.
Pedir en el puesto de la plaza: tú hablas primero ("deme tres libras de tomate") y el vendedor contesta. El vendedor nunca te llama a la casa para ofrecerte algo.
Escribir https://dummyjson.com/products?limit=3 en la barra produce una petición GET y una respuesta 200 OK con un JSON.
Pensar que el servidor "manda" datos nuevos por su cuenta. En HTTP siempre habla primero el cliente; si quieres datos frescos, vuelves a pedirlos.

Escribes la dirección y pulsas Enter. ¿Quién habla primero?

Habla primero siempre el cliente. El servidor está encendido esperando y solo contesta. Reproduce el flujo de la izquierda y fíjate en el orden de los dos paquetes.

La ruta es el puesto del mercado; el query string son las indicaciones al vendedor: "de los maduros, solo tres".
url.searchParams.set('q', 'miel de abeja') produce ?q=miel+de+abeja, ya codificado.
Armar la URL pegando textos. Un & dentro del dato parte el parámetro en dos y la petición pide otra cosa, sin ningún error visible.

Qué es una API y qué es JSON

El servidor puede estar escrito en C# y tu panel en JavaScript. ¿En qué idioma se entienden?

Contrato entre programas

Una API dice qué pedir y qué devuelve

APIInterfaz de programación de aplicaciones
Una API es un contrato: qué rutas existen, qué hay que enviar a cada una y qué devuelve. Mientras el servidor respete el contrato, no importa cómo está escrito por dentro.
La carta de un restaurante: dice qué puedes pedir y qué te llega. No te dice quién cocina ni con qué ollas.
GET /products?limit=1&select=title,price,stock,category devuelve { "products": [ ... ], "total": 194, "skip": 0, "limit": 1 }.
Escribir el panel pegado a los nombres de una API concreta (title, stock). Cuando llegue tu backend, tendrías que cambiar todo el código.

El problema de esperar

Pedir el catálogo tarda. Si JavaScript se quedara parado esperando, ¿qué le pasaría a la página?

Un solo hilo

Un hilo ocupado congela la página

Hilo únicoUna cosa a la vez
JavaScript corre tu código en un solo hilo. Mientras una función corre, nada más corre: ni clics, ni animaciones hechas con JavaScript, ni el pintado. Por eso esperar no puede ser trabajo de JavaScript: lo hacen las Web APIs del navegador, por fuera.
Un solo cajero en el puesto. Si se queda mirando la puerta a ver si llega el camión, la fila entera se detiene.
Un temporizador de 0 ms espera todo el ciclo while: no corre antes del tiempo indicado, y solo cuando el hilo esté libre.
Escribir un ciclo que "espera" a que llegue un dato. La página se congela y el dato tampoco llega antes.

Un temporizador garantiza que no corre antes de su tiempo, y solo cuando el hilo esté libre. Ejecuta el código y mira el orden.

Predice antes de seguir

¿En qué orden salen las letras?

Tres momentosSíncrono, microtareas y tareas
Cada línea pertenece a uno de tres momentos: código síncrono (ahora), microtareas (al vaciarse la pila) y tareas (después de todas las microtareas, una por vuelta).
En el puesto: primero se despacha a quien está en el mostrador; luego a los domicilios ya pagados; por último, a la fila general, de uno en uno.
Pregúntate por cada línea: ¿es síncrona, microtarea o tarea? ¿Qué quedó antes en la cola?
Creer que el temporizador gana porque su tiempo es 0. El tiempo es un mínimo, no un turno.
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');

El temporizador está en 0 milisegundos. ¿Qué imprime la consola?

Primero corre todo lo síncrono: A y D. Con la pila vacía, el bucle vacía las microtareas: C. Solo entonces toma la tarea del temporizador: B. Mira la figura de la izquierda: ahora sí se llena.
En el puesto se atiende primero el mostrador, luego los domicilios pagados y al final la fila general, de uno en uno.

Modelo mental

Pila, Web APIs y colas, paso a paso

Bucle de eventosLas cuatro reglas que se memorizan
El bucle de eventos repite: 1) corre lo síncrono hasta vaciar la pila; 2) vacía todas las microtareas, incluidas las que se agreguen mientras tanto; 3) toma una tarea; 4) vuelve al paso 2.
El vigilante de la fila: mientras el mostrador esté ocupado, nadie pasa; cuando se libera, primero los domicilios pagados, después uno de la fila.
Elige el programa 6 y mira cómo then 2 se encola solo cuando termina then 1.
Pensar que las tareas se atienden todas juntas: después de cada tarea, el bucle vuelve a las microtareas.

Programa 1: Temporizador en 0. Los diez programas coinciden con la salida real de Node.

Se memoriza poco, se razona mucho

Ordena la salida con las reglas

Cómo razonarDos preguntas por línea
Se memorizan las cuatro reglas del bucle. No se memoriza cada orden: se razona. Para cada línea pregunta: ¿es síncrona, microtarea o tarea? ¿Qué quedó antes en su cola?
Como ordenar quién pasa al mostrador sabiendo las reglas de la fila, sin haber visto ese día antes.
En una función async, lo que va antes del primer await es síncrono; lo que va después es una microtarea.
Olvidar que, tras cada tarea, el bucle vacía otra vez las microtareas.
El bucle empieza por lo síncrono.

Modelo mental

          
Pendiente, cumplida o rechazada

        

        

          PromesaUn resultado que llegará después
          

            
Una promesa empieza pendiente y pasa una sola vez a cumplida (con un valor) o a rechazada (con un motivo). Ya resuelta, no vuelve a cambiar.

            
El ficho del jugo: mientras lo licúan está pendiente; luego te entregan el jugo o te devuelven el ficho porque se acabó la fruta.

            
new Promise((resolve, reject) => ...) recibe una función que corre de inmediato con resolve para cumplir y reject para rechazar.

Encadenamiento

          
Un error salta hasta el catch

        

        

          then, catch y finallyQué recibe cada uno
          

            
then corre si la promesa se cumple y recibe el valor; catch corre si se rechaza, o si un paso anterior lanzó un error; finally corre siempre y no recibe nada. Cada then devuelve una promesa nueva: eso permite encadenar.

            
Una cadena de manos pasando bultos. Si a una mano se le cae el bulto, las siguientes no reciben nada hasta que alguien recoge el problema.

            
finally es el sitio natural para esconder el aviso "Cargando...".

            
Olvidar el return dentro de un then con llaves: el siguiente recibe undefined.

          

        

      

      

        

          
Promise.resolve(2)
  .then((n) => n * 10)
  .then((n) => { console.log(n); return n + 1; })
  .then((n) => { throw new Error('falló en ' + n); })
  .then(() => console.log('esto no se imprime'))
  .catch((e) => console.log('catch:', e.message))
  .finally(() => console.log('finally'));

          

          

            
MétodoCorre cuandoRecibe

            
              
.then(f)la promesa se cumpleel valor

              
.catch(f)se rechaza o algo lanzóel error

async function pedirJSON(ruta, opciones = {}) {
  let respuesta;
  try {
    respuesta = await fetch(URL_BASE + ruta, {
      ...opciones,
      signal: AbortSignal.timeout(TIEMPO_MAXIMO_MS),
    });
  } catch (error) {
    if (error.name === 'TimeoutError') {
      throw new ErrorApi('La API tardó demasiado en responder.', 'tiempo');
    }
    throw new ErrorApi('No hay conexión con el servidor.', 'red');
  }
  if (!respuesta.ok) {
    throw new ErrorApi(`El servidor respondió ${respuesta.status}.`, 'http', respuesta.status);
  }
  try {
    return await respuesta.json();
  } catch {
    throw new ErrorApi('La respuesta no es un JSON válido.', 'formato');
  }
}

Reintento

          
Reintentar, pero cada vez más tarde

        

        

          Espera crecienteExponential backoff
          

            
El reintento con espera creciente duplica la espera tras cada fallo: 500, 1000, 2000 ms. Solo se reintentan fallas pasajeras: red, tiempo agotado y 5xx. Un 4xx no cambiará por repetirlo.

            
Si el puesto está lleno, vuelves en cinco minutos y luego en diez. Si todos gritan cada segundo, nadie es atendido.

            
tarea es una función que hace la petición, no la petición ya hecha: hay que poder repetirla.

            
Reintentar solo un POST que crea un pedido: si el primero sí llegó y se perdió la respuesta, se crea dos veces.

          

        

      

      

        
const esperar = (ms) => new Promise((r) => setTimeout(r, ms));

async function conReintentos(tarea, intentos = 3, base = 500) {
  for (let n = 1; n <= intentos; n++) {
    try {
      return await tarea();
    } catch (error) {
      const sePuede = error.tipo === 'red' || error.tipo === 'tiempo'
        || (error.tipo === 'http' && error.estado >= 500);
      if (!sePuede || n === intentos) throw error;
      const espera = base * 2 ** (n - 1);
      console.warn(`Intento ${n} falló. Reintento en ${espera} ms.`);
      await esperar(espera);
    }
  }
}
