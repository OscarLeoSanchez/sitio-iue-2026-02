Actividad: proyecto funcionando

Entregable final del proyecto. Programación Móvil (IF2004), grupos 601 y 602

Objetivo

Tu equipo entrega la aplicación móvil completa y funcionando que definió en el primer entregable. La app usa almacenamiento en la nube y almacenamiento local, funciona también sin conexión, trae datos de una API, tiene una arquitectura organizada y seguridad. Además, el repositorio cuenta, con su historial de cambios, cómo se construyó y quién aportó qué.

Se entrega el enlace al repositorio de GitHub del equipo. El proyecto debe poder ejecutarse desde el código siguiendo el README, y en la sustentación se muestra funcionando en un dispositivo real o en un emulador.

Los ejemplos de esta página usan el proyecto ficticio SalaYa, una app para reservar salas de estudio de una biblioteca, el mismo del primer entregable. Sirven para mostrar el nivel de detalle esperado. Tu proyecto es el que tu equipo definió.

Condiciones mínimas del proyecto

La app tiene que cumplir lo que el equipo definió en el primer entregable, al menos todos los requerimientos de prioridad alta. Además, sea cual sea el tema, incluye como mínimo lo siguiente:

CondiciónQué se verifica
Autenticación en la nubeRegistro e inicio de sesión con Firebase Authentication, con los roles que el proyecto necesite y lo que puede hacer cada uno.
Datos en la nubeLos datos del proyecto viven en Firestore, protegidos con reglas de seguridad. Un usuario solo lee y escribe lo que su rol permite.
Base de datos localSQLite guarda una copia de los datos principales, para consultarlos sin conexión.
Preferencias localesLa configuración del usuario (por ejemplo tema claro u oscuro, o un filtro favorito) se conserva entre aperturas.
Almacenamiento seguroLa sesión, el token o cualquier credencial se guardan en almacenamiento seguro, nunca en texto plano ni en preferencias.
Comportamiento sin conexiónSin internet, la app muestra lo último guardado con un aviso. Las acciones que necesitan conexión se bloquean y explican por qué, sin cerrarse ni perder lo escrito.
Estados de la interfazToda pantalla que carga datos remotos muestra los estados de carga, vacío y error.
NotificacionesAl menos un caso de notificación local o push que responda a un evento del proyecto.
ArquitecturaCódigo organizado en capas (presentación, dominio y datos), con repositorios y una fuente de datos intercambiable entre la nube y lo local.
SeguridadNinguna clave privada ni credencial dentro del repositorio. Las reglas de Firestore no están abiertas a todo el mundo.
Datos de una APILa app consume al menos una API REST (pública, propia o de un servicio) y muestra sus datos: petición HTTP, conversión del JSON a modelos, tiempos de espera y manejo de errores y reintentos. Si la API pide clave, la clave no está en el repositorio.

El README para ejecutar el proyecto

El README es la puerta de entrada al proyecto. Debe permitir que otra persona ejecute el proyecto sin preguntarle al equipo. Incluye:

  • Nombre del proyecto, integrantes y una captura de pantalla.
  • Versiones exactas de Flutter y Dart, y los comandos para ejecutar: flutter pub get y flutter run.
  • Qué archivos de configuración de Firebase y qué claves hacen falta, cómo se generan y dónde se colocan. Los archivos privados no van en el repositorio: se incluye un archivo de ejemplo con los nombres de las variables y sin sus valores.
  • Los usuarios de ejemplo de cada rol, para entrar a la app durante la sustentación.
  • El enlace a docs/definicion.md.

Historial de cambios en Git

  • Todos los integrantes hacen aportes reales, repartidos en funcionalidades distintas y no solo en documentación o en cambios de formato.
  • Una rama por funcionalidad, con nombres que digan qué hace (por ejemplo feature/modo-sin-conexion).
  • Pull Request para integrar a main, revisado y aprobado por un integrante distinto de quien lo escribió. Nadie fusiona su propio Pull Request.
  • Commits pequeños y claros, con mensajes que digan qué se hizo, en formato de commits convencionales (feat:, fix:, docs:).
  • El historial no se reescribe: no se borran ni se reemplazan commits para esconder errores o aportes.
  • El .gitignore de Flutter está presente, y no hay claves, archivos de configuración privados ni la carpeta build/ en el repositorio.
El historial se revisa por persona. El docente revisa en GitHub los commits y los Pull Requests de cada integrante, y los contrasta con la tabla de la sección 16 del documento. Un integrante sin aportes reales en el historial recibe 0 en el criterio de Git y no recibe la nota de equipo completa en los demás criterios. Declarar un aporte que el historial no respalda es una falta de integridad académica.

Sustentación

Todos los integrantes participan. El docente informa el tiempo disponible por equipo, y la nota de la sustentación es individual.

ParteQué se muestra
No técnicaEl problema, la solución y el recorrido de cada rol por la app funcionando.
TécnicaLos casos sin conexión y de error, la arquitectura, el almacenamiento, la API y el historial de Git.
PreguntasPreguntas del docente a cada integrante sobre el proyecto y sobre lo que aportó en Git.
Se sustenta con una presentación, no con un documento. El equipo prepara diapositivas y las guarda en docs/presentacion/. No se permite sustentar mostrando el README ni el docs/definicion.md completos en pantalla, ni leerlos. Fuera de las diapositivas solo se muestra la demo en vivo de la app, el historial de GitHub y, si una pregunta lo requiere, el código.

Parte no técnica

Dirigida a alguien que no programa, como un cliente. Cubre:

  • El problema y la solución: qué pasaba antes y qué cambia con la app.
  • La demo del flujo principal de cada rol, en un dispositivo real o en un emulador, con datos que viajan a la nube y regresan.
  • Lo que quedó fuera: qué se recortó del alcance original y por qué.

Parte técnica

Dirigida a otros desarrolladores. Cubre:

  • Demo del modo sin conexión: se apaga la conexión, se muestra lo guardado y se intenta una acción bloqueada.
  • Demo de un caso de error con su mensaje claro.
  • El almacenamiento: qué dato vive en la nube, cuál en local, y las reglas de seguridad que lo protegen.
  • La arquitectura en capas y cómo se intercambia la fuente de datos.
  • La API: cuál se consume, qué datos trae, cómo se convierten a modelos y qué pasa cuando la petición falla o tarda demasiado.
  • El historial de Git: ramas, Pull Requests y el aporte de cada integrante.

Advertencias

  • El uso de inteligencia artificial está permitido como apoyo, no para construir el proyecto completo. La declaración de uso de inteligencia artificial del documento sigue siendo obligatoria y se actualiza con lo que se usó durante el semestre. Declarar el uso no resta puntos. Usar IA sin declararlo, o no poder explicar lo que se entregó, sí.
  • Si la demo no ejecuta durante la sustentación, la funcionalidad se califica solo con lo que se pueda comprobar en el repositorio, y como máximo en el nivel Aceptable.
  • No se reciben archivos PDF ni Word. Si el repositorio es privado, la entrega no se puede calificar.
  • Las claves privadas nunca se suben a Git. Si una clave se sube por error, se revoca de inmediato y se genera una nueva: borrar el commit no basta porque la clave queda en el historial.
