Actividad: proyecto funcionando

Entregable final del proyecto. Programación Web (IF2003), grupo 603

Objetivo

Tu equipo entrega la plataforma web completa y funcionando que definió en el primer entregable. La plataforma guarda su información en una base de datos relacional, expone y consume una API propia, valida los datos en el cliente y en el servidor, controla el acceso por roles y está publicada en internet. Además, el repositorio cuenta, con su historial de cambios, cómo se construyó y quién aportó qué.

Se entrega el enlace al repositorio de GitHub del equipo y la dirección pública de la plataforma publicada. El proyecto también debe poder ejecutarse en local siguiendo el README, y en la sustentación se muestra funcionando en la dirección pública.

Los ejemplos de esta página usan el proyecto ficticio SalaYa, una plataforma para reservar salas de estudio de una biblioteca, el mismo del primer entregable. Sirven para mostrar el nivel de detalle esperado. Tu proyecto es el que tu equipo definió.

Condiciones mínimas del proyecto

La plataforma tiene que cumplir lo que el equipo definió en el primer entregable, al menos todos los requerimientos de prioridad alta. Además, sea cual sea el tema, incluye como mínimo lo siguiente:

CondiciónQué se verifica
Arquitectura MVCModelos, vistas y controladores separados, con rutas propias y servicios inyectados donde corresponda. La lógica no vive en las vistas.
Vistas con RazorUn layout común, vistas parciales para lo que se repite y vistas que reciben su modelo desde el controlador.
Formularios validadosAl menos un formulario con validación en el navegador y en el servidor. El servidor rechaza los datos inválidos aunque se salte la validación del navegador, y muestra el error sin borrar lo que el usuario escribió.
Base de datos relacionalUna base de datos relacional a elección del equipo, como PostgreSQL, SQL Server u otra, usada con Entity Framework Core y migraciones. Al menos tres entidades relacionadas, con CRUD completo (crear, consultar, editar y eliminar) de las principales y consultas LINQ.
Inicio de sesión y rolesLogin y al menos dos roles con permisos distintos. Los permisos se aplican en el servidor: una persona sin el rol no puede entrar a una ruta restringida escribiendo su dirección.
API propiaUna API REST con los endpoints que el proyecto necesita, documentada con OpenAPI, y consumida desde el frontend de la plataforma con fetch, con manejo de errores.
Páginas de estadoUna página de error clara y una página para recursos que no existen. Las listas vacías muestran un aviso en lugar de una pantalla en blanco.
PublicaciónLa plataforma está publicada en Azure App Service, con la base de datos en un servicio en la nube, y es accesible desde una dirección pública. La publicación se hace desde GitHub de forma continua.
Configuración por entornosLa plataforma funciona en local y en producción con configuración distinta. Las cadenas de conexión y los secretos se manejan con variables de entorno o secretos de usuario, nunca dentro del repositorio.
SeguridadContraseñas cifradas, ninguna clave ni cadena de conexión en el repositorio, y rutas y endpoints protegidos según el rol.

El README para ejecutar el proyecto

El README es la puerta de entrada al proyecto. Debe permitir que otra persona ejecute la plataforma en local sin preguntarle al equipo. Incluye:

  • Nombre del proyecto, integrantes, una captura de pantalla y la dirección pública de la plataforma.
  • La versión exacta del SDK de .NET y los comandos para ejecutar: dotnet restore, dotnet ef database update y dotnet run.
  • Qué base de datos se usa y cómo tenerla en local, qué configuración hace falta (cadena de conexión y secretos), cómo se establece y dónde. Los valores privados no van en el repositorio: se incluye un archivo de ejemplo con los nombres de las variables y sin sus valores.
  • Los usuarios de ejemplo de cada rol, para entrar a la plataforma durante la sustentación.
  • El enlace a docs/definicion.md.

Historial de cambios en Git

  • Todos los integrantes hacen aportes reales, repartidos en funcionalidades distintas y no solo en documentación o en cambios de formato.
  • Una rama por funcionalidad, con nombres que digan qué hace (por ejemplo feature/api-reservas).
  • Pull Request para integrar a main, revisado y aprobado por un integrante distinto de quien lo escribió. Nadie fusiona su propio Pull Request.
  • Commits pequeños y claros, con mensajes que digan qué se hizo, en formato de commits convencionales (feat:, fix:, docs:).
  • El historial no se reescribe: no se borran ni se reemplazan commits para esconder errores o aportes.
  • El .gitignore de .NET está presente, y no hay cadenas de conexión, claves ni las carpetas bin/ y obj/ en el repositorio.
El historial se revisa por persona. El docente revisa en GitHub los commits y los Pull Requests de cada integrante, y los contrasta con la tabla de la sección 16 del documento. Un integrante sin aportes reales en el historial recibe 0 en el criterio de Git y no recibe la nota de equipo completa en los demás criterios. Declarar un aporte que el historial no respalda es una falta de integridad académica.

Sustentación

Todos los integrantes participan. El docente informa el tiempo disponible por equipo, y la nota de la sustentación es individual.

ParteQué se muestra
No técnicaEl problema, la solución y el recorrido de cada rol por la plataforma publicada.
TécnicaLa validación, los roles, la base de datos, la API, la publicación y el historial de Git.
PreguntasPreguntas del docente a cada integrante sobre el proyecto y sobre lo que aportó en Git.
Se sustenta con una presentación, no con un documento. El equipo prepara diapositivas y las guarda en docs/presentacion/. No se permite sustentar mostrando el README ni el docs/definicion.md completos en pantalla, ni leerlos. Fuera de las diapositivas solo se muestra la demo en vivo de la plataforma, el historial de GitHub y, si una pregunta lo requiere, el código.

Parte no técnica

Dirigida a alguien que no programa, como un cliente. Cubre:

  • El problema y la solución: qué pasaba antes y qué cambia con la plataforma.
  • La demo del flujo principal de cada rol, en la dirección pública, con datos que se guardan y se consultan.
  • Lo que quedó fuera: qué se recortó del alcance original y por qué.

Parte técnica

Dirigida a otros desarrolladores. Cubre:

  • Demo de la validación: se envía un formulario inválido y se muestra el error en el navegador y en el servidor.
  • Demo de los roles: una persona sin el rol intenta entrar a una ruta restringida.
  • La base de datos elegida y por qué, el modelo de datos, las migraciones y una consulta LINQ importante.
  • La API: los endpoints, su documentación OpenAPI y cómo el frontend la consume y maneja los errores.
  • La publicación: cómo se despliega desde GitHub y qué cambia entre local y producción.
  • El historial de Git: ramas, Pull Requests y el aporte de cada integrante.

Advertencias

  • El uso de inteligencia artificial está permitido como apoyo, no para construir el proyecto completo. La declaración de uso de inteligencia artificial del documento sigue siendo obligatoria y se actualiza con lo que se usó durante el semestre. Declarar el uso no resta puntos. Usar IA sin declararlo, o no poder explicar lo que se entregó, sí.
  • Si la plataforma publicada no responde durante la sustentación, la funcionalidad se califica solo con lo que se pueda comprobar en el repositorio, y como máximo en el nivel Aceptable.
  • No se reciben archivos PDF ni Word. Si el repositorio es privado, la entrega no se puede calificar.
  • Las cadenas de conexión y las claves nunca se suben a Git. Si una se sube por error, se cambia de inmediato y se genera una nueva: borrar el commit no basta porque el valor queda en el historial.
